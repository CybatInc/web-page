Critical Security Specs_

Permissions (IAM)

The Engine operates under a principle of least privilege. SDK ingestion itself requires zero IAM grants in your project — authentication is a single API key, validated at the edge by API Gateway. Enabling automatic blocking (optional) requires granting compute.securityAdmin (Cloud Armor enforcement) and compute.networkViewer (VPC discovery) on the specific project you configure, not your whole organization.

Data Sovereignty

Zero-retention architecture ensures request telemetry is evaluated in-stream and immediately discarded. No request bodies or sensitive payload data are persisted to Cybat infrastructure — only the anonymized (HMAC-hashed) verdict needed for repeat-offender caching.

Authentication

Platform access relies exclusively on Single Sign-On (SSO) via Google Identity integration, seamlessly authorizing users against their existing Workspace/Cloud Identity directory.

Client Requirements_

Minimum setup needed for the engine to detect — and optionally block — threats effectively.

Infrastructure Prerequisites

Required

  • ✓ An app that can install the Cybat SDK as middleware (Node.js today; Python and Go on the roadmap)
  • ✓ A valid, non-revoked, non-expired API key from the Intelligence Portal
  • ✓ Slack workspace for real-time alert delivery

Recommended

  • + gcpProjectId configured on the SDK — enables automatic VPC Firewall / Cloud Armor blocking, not just detection
  • + compute.securityAdmin + compute.networkViewer granted on that specific project — scoped, not org-wide
  • + app.set('trust proxy', ...) if your app sits behind your own load balancer — otherwise the SDK reports the proxy's IP instead of the real client's

How the SDK Reports Data

Auth

API Key, Validated at the Edge

Every batch is sent with an x-api-key header. API Gateway validates it's a real, non-deleted key before the request ever reaches our compute — invalid, expired, or revoked keys are rejected at the network edge.

Batching

Buffered, Not Per-Request

The SDK buffers captured requests in memory and flushes every ~2 seconds (or when the batch fills up) — never one HTTP call per request. A failed send is retried a bounded number of times, then dropped rather than queued forever.

Buffering

Pub/Sub, Not a Queue in Your App

Once past the API Gateway, batches land on a durable Pub/Sub topic before reaching the AI analysis engine — a traffic spike (exactly when a real attack is happening) is absorbed instead of dropped.

Event Fields

Field Status Purpose
remoteIp Required Source IP for grouping and blocking. Captured automatically by the SDK from the request.
method, url, status Required Drive SQLi, XSS, path traversal, and credential-stuffing detection. Captured automatically — status is read after your handler responds, not before.
userAgent, referer Recommended Distinguishes legitimate browser traffic from scanning tools and bots. Captured automatically.
gcpProjectId Optional Set once at SDK initiation. Required for automatic enforcement — without it, the engine detects and alerts but never modifies infrastructure.
serviceName Optional A label shown on incidents — useful if one API key covers multiple services.

Limitations & Out-of-Scope

  • ✗ Automatic enforcement without a project ID: Detection works regardless of where your app runs, but blocking a threat requires telling the SDK which cloud project to act on — otherwise nothing gets modified.
  • ✗ AWS enforcement: Detection is available today for apps anywhere; automatic blocking on AWS infrastructure is on the roadmap and not yet live.
  • ✗ Infrastructure-layer attacks: The SDK sees application-level HTTP traffic only. Network-layer signals (VPC port scanning, IAM audit escalation) still require the legacy Log Sink integration.
  • ✗ Encrypted payload inspection: The engine operates on request metadata. It does not decrypt or inspect TLS payload bodies.
  • ✗ Non-HTTP protocols: Raw TCP/UDP, DNS, and SMTP attack patterns are outside the current detection scope.
