Especificaciones Críticas de Seguridad_

Permisos (IAM)

El Motor opera bajo el principio de privilegio mínimo. La ingesta del SDK por sí misma no requiere asignaciones de IAM en su proyecto; la autenticación es una única clave API validada en el borde por API Gateway. No se requieren sumideros ni permisos de configuración de logs. La activación del bloqueo automático (opcional) requiere otorgar roles con alcance delimitado: compute.securityAdmin (aplicación de reglas en Cloud Armor y VPC Firewall), compute.networkViewer (inspección de topología de red) y browser en su proyecto u organización configurada. El portal de incorporación proporciona un comando de Cloud Shell de una sola línea y copiable para aplicar estos roles.

Soberanía de Datos

La arquitectura de retención cero garantiza que la telemetría de solicitudes se evalúa en flujo y se descarta inmediatamente. Ningún cuerpo de solicitud ni datos confidenciales de carga útil se persisten en la infraestructura de Cybat; solo se conserva el veredicto anonimizado (con hash HMAC) necesario para el almacenamiento en caché de infractores recurrentes.

Autenticación

El acceso a la plataforma se basa exclusivamente en Inicio de Sesión Único (SSO) mediante Google Identity, autorizando a los usuarios sin problemas con su directorio existente de Workspace/Cloud Identity.

Requisitos del Cliente_

Configuración mínima requerida para que el motor detecte —y opcionalmente bloquee— amenazas de manera efectiva.

Requisitos Previos de Infraestructura

Requerido

  • ✓ Una aplicación que pueda instalar el SDK de Cybat como middleware (Python, Node.js, PHP y Java activos hoy; Go próximamente)
  • ✓ Una clave API válida, no revocada y no expirada del Portal de Inteligencia
  • ✓ Espacio de trabajo de Slack para la entrega de alertas en tiempo real

Recomendado

  • + gcpProjectId configurado en el SDK: habilita el bloqueo automático en VPC Firewall / Cloud Armor, no solo la detección
  • + Roles de IAM delimitados otorgados mediante el comando de Cloud Shell del portal (compute.securityAdmin, compute.networkViewer y browser): desbloquea la remediación automatizada y el desbloqueo en un clic desde el panel
  • + app.set('trust proxy', ...) (o equivalente de su framework) si su aplicación reside detrás de un balanceador de carga: asegura que el SDK reporte la IP real del cliente

Cómo Reporta Datos el SDK

Autenticación

Clave API, Validada en el Borde

Cada lote se envía con una cabecera x-api-key. API Gateway valida que sea una clave real y activa antes de que la petición llegue a nuestras instancias de cómputo; las claves inválidas, vencidas o revocadas se rechazan en el borde de la red.

Agrupación por Lotes

En Búfer, No por Petición

El SDK almacena las peticiones capturadas en memoria y las envía cada ~2 segundos (o cuando se llena el lote), nunca una llamada HTTP por petición individual. Los envíos fallidos se reintentan un número acotado de veces y luego se descartan para evitar colas infinitas.

Amortiguación

Pub/Sub, Sin Colas en su Aplicación

Una vez superado el API Gateway, los lotes ingresan a un tema duradero de Pub/Sub antes de llegar al motor de análisis de IA: los picos de tráfico (precisamente cuando ocurre un ataque real) se absorben sin pérdidas.

Campos del Evento

Campo Estado Propósito
remoteIp Requerido IP de origen para agrupación y bloqueo. Capturada automáticamente por el SDK desde la solicitud.
method, url, status Requerido Fundamentales para detección de SQLi, XSS, salto de directorios y relleno de credenciales. Capturados automáticamente; el código de estado se lee después de que su controlador responde, no antes.
userAgent, referer Recomendado Distingue el tráfico legítimo de navegadores frente a herramientas de escaneo y bots. Capturados automáticamente.
gcpProjectId Opcional Configurado al iniciar el SDK. Requerido para bloqueo automático: sin él, el motor detecta y alerta pero nunca modifica la infraestructura.
serviceName Opcional Etiqueta mostrada en incidentes: útil si una sola clave API cubre múltiples microservicios.

Limitaciones y Fuera de Alcance

  • ✗ Bloqueo automático sin project ID: La detección funciona sin importar dónde se ejecute su app, pero bloquear una amenaza requiere indicar al SDK qué proyecto en la nube modificar; de lo contrario, nada se altera.
  • ✗ Bloqueo en AWS: La detección está disponible hoy para aplicaciones en cualquier lugar; el bloqueo automático en infraestructura de AWS está en la hoja de ruta y aún no está activo.
  • ✗ Ataques a nivel de infraestructura: El SDK opera como middleware a nivel de aplicación inspeccionando tráfico HTTP/HTTPS. Las señales a nivel de red (escaneo de puertos VPC, eventos de auditoría IAM) quedan fuera del alcance del SDK.
  • ✗ Inspección de cargas útiles cifradas: El motor opera con metadatos de las peticiones. No descifra ni inspecciona los cuerpos de carga útil TLS crudos.
  • ✗ Protocolos no HTTP: Los patrones de ataque en TCP/UDP puros, DNS y SMTP quedan fuera del alcance de detección actual.
